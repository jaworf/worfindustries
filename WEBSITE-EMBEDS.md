# Church website embeds

Admins can open Web Settings → Put the app on your church’s website, enter approved HTTPS website addresses, and save their sharing choices. Copy the generated iframe into the website editor’s Custom HTML or Embed block. Include both www and non-www addresses when needed; the iframe height can be adjusted in the copied code.

The recommended login-required option loads the full ministry workspace inside the church’s branded page. The visitor’s address bar stays on the church website; the embedded app is still served from the app’s secure origin. Each person uses their own app account, and existing church and role permissions remain enforced. An account belonging to another church is rejected before workspace records are loaded. Account setup, participant assessments, support, and browser-specific sign-in fallback links may open separately.

The Limited public directory requires explicit public-directory publishing and iframe enablement. Its anonymous API, screen, PDF download and printable PDF expose exactly ministry, volunteer name and term for approved active public records. Contact details, private or public notes, positions, vote dates, recruitment history, assessments and ordination are excluded. The public view has no login or editing controls. Both Settings options remain open in matching padded cards. This configuration is web-only. A password on the containing website does not protect a separate anonymous iframe or directory URL. Use the login-required option for private access; an additional password-protected staff page is recommended.

Website settings and publishing changes require a church admin. New embed settings start disabled with no approved hosts. Previously applied migrations are unchanged. New forward migrations add settings, checked configuration functions, the three-field directory API, and authenticated account-scoped church branding. The older broad directory view is no longer anonymously readable. Bootstrap metadata intentionally allows anonymous reads of only an enabled church’s name, slug, and approved frame origins, so the browser can load its login page. It does not grant data access, expose credentials, or give anonymous access to the settings table or private schema.

Framing is restricted with Content-Security-Policy to the saved origins for that church and mode. Disabled, mismatched, or failed configuration lookups fail closed. Normal admin routes remain protected from third-party framing. Existing legacy directory pages remain scoped to Riverview; other church embeds use their explicit slug. Signed-in headers and account setup use the account’s church name; generic sign-in screens use neutral branding until the church is known.

Validation covers admin/editor/viewer permissions, cross-church configuration isolation, unsafe origins, public-sharing opt-in and revocation, bootstrap field limits, framing headers, disabled routes, escaped iframe code, mobile Settings layout, matching-church sign-in, and rejection of a different church before record requests. Browser authentication tests use fictional accounts and an intercepted API, never real credentials. Some browsers restrict storage inside another site; the login screen offers a secure new-tab fallback.
